# 2026.287.2222 — fix(add_candy): fail loudly when a pinned ref cannot be honoured, instead of running another version's plan

## Summary

`rp.CandyModels` is keyed by candy **identity** (`BareRef`: no `@`, no `:version`), which is right
for the graph — `include:`/`require:` edges are bare refs and the dep walk is literally
`layers[BareCandyRef(ref)]` — but it **cannot distinguish two coordinates of one repo**. When two
scopes in the same project pin the same repo at different tags, the loader FETCHES both
(`sdk/loaderkit/refs_collect.go`'s per-`(repo, tag)` fetch set, `scan_orchestrate.go`'s
`materials[repoVer{repo,ver}]`) and then `PickCandyVersion` keeps **one** winner per identity — the
losers are dropped at exactly that point. So `candyAddSteps`' bare lookup returns the arbiter's
winner whatever the deploy pinned.

**This change is the MISSED CONTROL, not the fix.** The scan already stamps the winning source git
tag onto the model (`ws.Model.Version = winner.GitTag`), which makes the collision *detectable*: an
authored ref that names a version and receives a model stamped with a **different** one is an
unresolvable input, not a plan to run. It now fails loudly (infra exit) naming the ref, the wanted
version, the model's version and the issue, instead of silently asserting a version the deploy never
named. The guard is narrow by construction:

* a **version-less** ref keeps the identity lookup — there is no pin to honour;
* an **unstamped** model (`Version == ""`) is not gated — that is the documented local-shadow case
  (a local candy of the same name wins, as INFO, and carries no git tag);
* a local **bare-name** ref has no version at all.

**It does NOT unblock `opencharly/distro-arch#52`** — and it says so. The pin still cannot be
honoured here; with this guard in the tree `#52`'s child phase fails LOUDLY (naming both versions)
rather than quietly asserting the wrong one. A guard that pretended to unblock would be the fake fix.
Honouring the pin needs the per-coordinate models carried on the resolved-project envelope: a
`#ResolvedProject` field (`spec/schema/resolvedproject.cue`, CUE-sourced → `cue-gen`) plus the
loader's exit — which is the **seam method** `ScanCandyFromLocal` (`spec/spec/loader_seam.go:362`)
with **7 call sites across charly, plugin-build ×4 legs, plugin-loader and the vendored charly
mirrors**. That is filed as the next row in `opencharly/plugin-check#112`, never half-landed.

**The cheap green is refused in writing on `#112`**: making the whole project agree on ONE coordinate
for that repo (a `layer-agent-forwarding` tag + three box bumps) would turn `#52` green while the
bare-keyed lookup kept silently ignoring pins — the next pin bump anywhere would re-open the class
with the same silence.
