# 2026.255.1732 — fix(check): --steps-file reads the AUTHORING form (+ pin the sdk seam it uses)

## Summary

Make **`charly check live --steps-file`** accept the **authoring form** the plan docs teach, and pin the sdk seam that makes it possible.

### The defect, proven live (the G-8 assets, 2026-09-12)

| committed asset, run as authored | result |
|---|---|
| `screencap-live-steps.yml` | **exit 1** — `cannot unmarshal !!map into string` |
| `screencap-negative-control-steps.yml` | **exit 2** with `check has no verb set` — a **FALSE PASS**: it exited 2 *without ever running a step*, which is a passing-looking result for a check that never executed |
| a matcher shorthand alone | `unsupported matcher op ""` |

**Root cause.** `--steps-file` raw-`yaml.Unmarshal`led straight into `[]spec.Step`:

- `spec.Op` has **no per-verb fields, no catch-all and no `UnmarshalYAML`** — so the canonical `<word>: <input>` plugin-verb sugar was **silently dropped**, and the step reached the engine with no verb at all;
- `spec.MatcherList` implements **`UnmarshalJSON` but not `UnmarshalYAML`** — so the `{contains: x}` shorthand lost its operator.

The desugar lives only in the loader (`sdk/loaderkit`), and the JSON-aware decode only on the JSON path — which is exactly the pair the loader uses to read an entity plan. A user-authored step list is the same authoring surface, so it must be read the same way.

### The fix

`parseStepsFile` (extracted from the inline block so it is testable) now:

1. parses to a `yaml.Node` and runs **`loaderkit.DesugarSteps`** — the seam exported by **opencharly/sdk#252** (merged 17:08:24Z);
2. decodes through **JSON**, so spec's own unmarshalers (the matcher shorthand) apply.

The sdk pin moves to **`v0.2026255.1708`** — the tag that carries `DesugarSteps` — which also lifts its transitive requirement on `spec` to **`v0.2026254.503`**; both pins are part of this diff and are stated here rather than left to the lockfile.

**Also in this commit:** `candy/plugin-check/steps_file_test.go` is **restored**. An earlier revision of this change OVERWROTE that file, silently dropping `TestWrapStepsFileSet` — the only coverage of `wrapStepsFileSet`, which is still live at three call sites (`live_gather.go:188/496/633`). Its removal was an R10 regression, not a tidy-up; the test is back verbatim and all three tests in the file pass.

## LIVE proof (A2/R10) — the changed path executing on a disposable bed

The defect was surfaced by a **live** run, so a unit test alone cannot close it. The sugar-form files were run through a dev binary built over this branch (`GOWORK` workspace: charly + this checkout, `sdk v0.2026255.1708`; `strings <bin> | grep -c DesugarSteps` → 2), against a **disposable** pod bed:

```console
$ charly box build sfp-live-evidence          # exit 0
$ charly deploy add sfp-live-evidence-check   # exit 0
$ charly config sfp-live-evidence-check       # exit 0
$ charly start sfp-live-evidence-check        # exit 0 — Status: running

$ charly check live sfp-live-evidence-check --steps-file positive.yml ; echo "POS-EXIT=$?"
Image: sfp-live-evidence (container: charly-sfp-live-evidence-check)
  PASS  check the sugar desugars live  [sfp-pos]  exit=0

1 step: 1 passed, 0 failed, 0 skipped
POS-EXIT=0

$ charly check live sfp-live-evidence-check --steps-file negative.yml ; echo "NEG-EXIT=$?"
Image: sfp-live-evidence (container: charly-sfp-live-evidence-check)
  FAIL  check the sugar desugars live - negative control  [sfp-neg]  exit=3, want 0 (stderr: )

1 step: 0 passed, 1 failed, 0 skipped
command "check": 1 check(s) failed
NEG-EXIT=2
```

The negative control **ran its step and failed its own `exit 3`** — the false-pass mode (*"exit 2 without ever running a step"*) is gone: `grep -c "no verb set"` over every fixed run → **0**.

The JSON form shows the sugar became the wire pair, with the step's own fields intact:

```json
"op": { "plugin": "command", "id": "sfp-pos",
        "plugin_input": { "command": "echo SUGAR-POSITIVE-RAN", "in_container": true },
        "origin": "steps-file", "intent_do": "assert" }
```

and the matcher shorthand (`stdout: {contains: SUGAR-POSITIVE-RAN}`) matched the command's real stdout — so the JSON-decode half is exercised live as well.

**The pre-fix contrast — the same files on an older binary** (`sdk v0.2026254.1740`, pre-#252):

| file | pre-fix | fixed |
|---|---|---|
| `positive.yml` | **exit 1** — `line 4: cannot unmarshal !!map into string` | **exit 0**, step ran |
| `negative.yml` | **exit 1** — the same parse error | **exit 2**, step ran and failed its own `exit 3` |
| `sugar-file.yml` | **exit 2** — `check has no verb set` (**the false pass**) | exit 0, step ran |
