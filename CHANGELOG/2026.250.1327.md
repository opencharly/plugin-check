# 2026.250.1327 — check: thread the VM's forwarded host ports into the check env vars + the mcp_provide URL (P4 VM substrate parity)

## Summary

P4 VM-substrate parity for the charly-mcp R10 bed (plan §3.9/§3.10): the check env's runtime vars + mcp_provide endpoint were container-venue-only. Two gaps the bed's check-live exposed:

1. **HOST_PORT:N vars for VM venues** — a VM's declared `network.port_forwards` entries did not exist as host-port runtime vars (only container venues have the inspection leg). `mergeVmForwardedHostPortVars` reads the VM's persisted auto-forward allocations (VmDeployState.PortForwards, written at vm-create) via the reverse-channel and threads them into the live-gather vars — the same grammar a pod bed's `addr:`/`http:`/`port:` checks use, now available for VM beds.
2. **The mcp_provide URL for auto-allocated forwards** — `hostRoutableMcpProvide` rewrites the guest-side URL (the env's mcp_provide, seeded from the vm template) to the persisted host-routable port for `auto:` allocations — the "guest address → host-routable address" translation the container label path performs via ResolveEndpoint, done where both the template URL and the persisted allocation are known.
