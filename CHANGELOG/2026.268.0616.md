# 2026.268.0616 — fix(check): honor a bed's own cpu:/ram: at vm create

## Summary of changes

Make a check bed's OWN authored `cpu:`/`ram:` actually reach `charly vm create`.

A check bed is a deploy whose `from:` names a `kind:vm` template. The bed engine creates the domain via `charly vm create <template-entity>` — which targets the TEMPLATE, so `plugin-vm`'s `vmShapeOverride` (which walks the template's `from:` chain) never sees the BED's own `cpu:`/`ram:`. The authored bed shape was a silent no-op: a bed capped at `cpu: 2` / `ram: 2G` still booted at the template size (measured 6 GB).

- `anchored.go` — new `seedBedVmShape(opts, bedNode)`: folds the decoded bed-root node's `Cpus`/`Ram` into `bedRunOpts`, unless the caller already set them (a roster-supplied cap wins).
- `bed_run.go` — `runCheckBed` calls `seedBedVmShape` on the decoded `bedNode`; `vmCreateArgs` then emits `--cpus`/`--ram`.
- `anchored_test.go` — `TestBedNodeShapeSeedsVmCreate` (bed-node shape seeds the argv; roster cap wins).

This also fixes the roster's per-VM cap: the `check-roster` `cpu:`/`ram:` already threaded to `vmCreateArgs`, but for a bed whose own shape was the source, nothing reached the domain.

**Closes / relates to:** the completed roster cutover (opencharly/plugin-check#55, opencharly/spec#154/#155, opencharly/sdk#281/#283).

**Breaking change + rollback:** a VM bed's domain now honors its authored shape. Rollback is a revert.
