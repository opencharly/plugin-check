# 2026.281.1011 — fix(check): dispose of a failed bed's venue by default — retention is an explicit opt-in (#75; supersedes auto-closed #89)

## Summary

`charly check run` reached its **venue** teardown only from the SUCCESS tail: `cleanup` and
`cleanup-members` are the last two entries of the bed's own step list, so every earlier
`return fail(...)` skipped them, printed `… left running for debugging`, and left the bed's
disposable target — for a VM bed a whole booted guest holding its vCPUs and RAM — up until some
later run of the SAME bed happened to reclaim it (`bed_run.go`'s pre-run reclaim masks the leak, so
nothing ever reports it). The **session** half of teardown has always had the every-exit-path
guarantee (the `bedTeardown` defer); the venue half had no equivalent. This change gives the venue
half the same reach, through one owner with one gate, and makes retention an explicit opt-in — the
shape the operator's STATUS correction on this issue asks for (keep the debugging affordance, stop
it applying by default). Closes #75.

**This PR replaces the auto-closed `#89`** (5 counting BLOCKs) with every finding fixed, on a fresh
branch off current `origin/main`. Round 5's three findings are the last ones, and all are answered
below: the §2 retention run on a superseded driver is deleted rather than relabelled (§2b(C) carries the retention branch on the published head), the success-path gate is restored to
its pre-change behaviour in code (Block 2 — the only code change of this round), and the out-of-repo
skill claim is proven out-of-repo (Block 3).

**One owner, three callers, ONE gate.** `bedVenueTeardown` is a named function over an explicit
`venueTeardownState` (`deployed` / `tornDown`), called from the success tail (Step 6, where a
teardown failure still fails the bed), from the failure tail `fail()`, and from a `defer` for the
panic path. The gate lives in that ONE owner and reads the SAME predicate every caller reads
(`keepVenue`); `cleanup` is a pure teardown body with no retention logic of its own, so a second
gate cannot drift from the first. One teardown body, no second tree walk, and no blind re-run of an
already-completed destroy.

**Retention is explicit, and scoped to the path that asked for it.** ONE predicate per path, and the
owner enforces whichever one its caller read:

- `keepVenueAlways(opts, root)` — path-independent: `--keep` / `--keep-venue` / a bed's
  `keep_venue:` policy, or a root that is **not** `disposable: true` (autonomous destroy is
  authorized only on an explicitly disposable target — the rulebook's Disposable-Only Autonomy).
  Read by the **success** tail.
- `keepVenueOnFailure(opts, root)` — `keepVenueAlways` plus the two requests that only ever mean
  "let me inspect a FAILURE": `--keep-on-failure` and a root's own `ephemeral.keep_on_failure:` (the
  field the score path already honours, `live_scoring.go`'s `ephemeralKeepOnFailure`, so the bed
  runner reads it rather than inventing a second retention rule). Read by the **failure** tail and by
  the panic-path defer — a panic IS a failure.
- `bedVenueTeardown(state, keep, teardown)` carries **no policy**: it enforces the caller's decision,
  once. A defer that enforces a different policy than the tail that just ran is therefore impossible
  to write by accident — which is exactly what review round 1 caught.

**Best-effort on the failure path.** `bedFailedVenue` returns the ORIGINAL step error either way: a
failed `vm destroy` is a warning line, never the error the operator reads.

**Stated bound (not an oversight), with a fresh live datum.** The SIGNAL path cannot be covered and
is not claimed: the signal handler re-raises with the default disposition, so nothing unwinds and no
deferred function runs (`spec/proc/cleanup.go:130-142`), and SIGKILL is uncatchable. That is why
`charly check stop` still prints the scoped destroy verb. Measured on 2026-10-08: a session
interruption killed a bed-runner mid-sequence, and `charly vm list` afterwards showed
`charly-check-r10-two-vm` and `charly-r10-vm-member` both `running` — the leak this issue reports,
reproduced by an interruption rather than argued from code. They were reclaimed with the scoped verbs
the notice/hints print (`charly vm destroy r10-vm --domain <domain> --if-exists --disk`, exit 0 each).

**Stale claims swept in the same change (R1/R5, and the operator's guidance rule).** The three
`deployed = true // keep it on any later failure` comments and `cleanup`'s doc said the opposite of
what the code does; `printDebugRetentionNotice` now documents that it is printed only on the
retention path; `check stop`'s comment cited "the same reason a FAILED bed leaves its target
running for debugging" — that default is gone, so it now names the signal path (its real, remaining
reason); and `bed_run.go`'s header sequence is annotated with the failure-path guarantee and its
explicit-retention escapes. The one live surface OUTSIDE this repo that carries the invalidated
claim is the generated `check` skill body (see "Guidance" below).
