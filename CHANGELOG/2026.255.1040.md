# 2026.255.1040 — feat(check): a third diagnostic tier — ADVISORY (reported, never gating)

## Summary

Add a **third diagnostic tier — ADVISORY** — and route the podman store nudge into it, so the check gate can express the distinction it actually needs:

| Tier | Meaning | Disposition |
|---|---|---|
| `severityError` | a **failure that MUST hard-fail** | `errors_fatal: true` — fails the step |
| `severityWarning` | a **defect in the change** | counted, reported; fails when `warnings_fatal` is staged |
| **`severityAdvisory` (NEW)** | a **condition of the host/environment** (e.g. a performance degradation) that must be fixed but is not a property of the change | counted and REPORTED (`advisories: N`, `advisories_fatal: false`) — **never fatal, under any policy** |

Changes: the `severityAdvisory` constant; a first-match-wins recognizer for `notice:`/`advisory:` placed ahead of the warning recognizer; `stepDiagnostics.Advisories`; the scan-loop bucket; both diagnostics writers emit `advisories:` (step) and `advisories: N` + `advisories_fatal: false` (run); **`bed_run.go` — the run-level fold is now the named helper `rollupStepDiagnostics` carrying `run.Advisories += s.Diag.Advisories`** (before it, the tier was counted per step and was structurally 0 in the run summary — found by the live A/B below), and `diagNotice` now carries `advisories=` in the per-step console suffix; and **two tests**: `TestAdvisoryTierIsReportedButNeverGating` and `TestAdvisoryCountReachesTheRunRollup`.

Nothing that used to fail stops failing: `errors_fatal` and `warnings_fatal` semantics are untouched, and this is a CLASSIFICATION correction at the source (the companion `plugin-build#11` stops emitting a documented non-blocker at `warning:` severity).

**Block 4 — "a generic non-gating escape hatch without sign-off or bed proof" (B14(c)/T4).** This is the substantive objection and it deserves a straight answer rather than a narrowing hack.

*Why the recognizer is deliberately generic.* The scanner reads RAW step logs; a severity prefix IS its protocol. Making the recognizer match only the one podman string would couple the check plugin to a specific emitter's wording — the next host-state line (`distro-cachyos#83` records a second class in the same run: 14× `candy pod-postgresql resolved to multiple versions`) would need another hard-coded string, and every such string is a place where the gate's behaviour changes by string-matching accident. The tier is the seam: ONE protocol, explicit, counted, reported, and policy-visible.

*What bounds the escape-hatch risk.* An advisory is never silent: it is counted (`advisories: N`), listed in the run summary next to `advisories_fatal: false`, and read by this validator. Relabelling a genuine defect as `notice:` therefore does not hide it — it prints it as a count the reviewer must account for, which is exactly the visibility a silent bypass would lack. The gate's hard-fail edges (`error:`, staged `warning:`) are untouched.

*T4 sign-off.* Introducing a tier that changes the gate's effective behaviour is precisely a T4 change, so the maintainer's explicit sign-off is recorded in a comment on this PR, and this PR is not to be merged without it. The alternative the review offers — narrowing to the specific emitter line — is declined with the reasoning above; if the maintainer prefers narrowing, the sign-off comment is the place to say so and this PR will be revised accordingly.

### The defect this live run exposed in THIS change (R1 — fixed in the same PR, not shipped)

The first live run showed the tier working at step level but **structurally 0 at run level**:

```yaml
  - name: image-build
    diagnostics:
      advisories: 1          # ← the step counted it
…
diagnostics:                 # ← the RUN rollup
  advisories: 0              # ← structural 0
```

Root cause (`bed_run.go`, `writeBedSummary`): the inline fold aggregated `run.Warnings/Errors/Allowlisted/CacheSteps/CacheHits/Findings` and **never `run.Advisories`**, so `writeRunDiagnostics` printed 0 at run level no matter what the steps said. Secondary: `diagNotice` omitted advisories from the per-step console suffix, so the PASS line read `[allowlisted=1 cache=0/18]`. A tier that is invisible at run level is not a reported tier, so it was fixed here:

- the fold is now ONE named helper, `rollupStepDiagnostics`, carrying every counter — so a future tier cannot silently miss the rollup;
- `diagNotice` now carries `advisories=`;
- pinned by `TestAdvisoryCountReachesTheRunRollup` (the rollup value across steps, the printed run block, the `advisories_fatal: false` line, and the console suffix), which **FAILS with the accumulation line removed**: `run rollup Advisories = 0, want 5`.

Live after the fix:

```yaml
diagnostics:                 # RUN rollup, after
  errors: 0
  warnings: 0
  advisories: 1
  advisories_fatal: false
```
```console
charly check run …: [image-build] PASS after 5.461s [advisories=1 allowlisted=1 cache=17/18]
```

Evidence retained: `/tmp/pb-live/evidence-PR/{box-build.stderr,image-build.log,summary.yml,bed-run.log}` and `/tmp/pb-live-project/.check/pb-live-evidence-check/2026.255.0942/`.

**What this does NOT prove (stated, not implied):** the bed is a purpose-built disposable bed (a sub-2-minute alpine project) driving the *same* `charly box build <image> --dev-local-pkg` step the product beds drive — it is not a product bed's product-bar. The product beds (`check-alpine-repo`, the distro beds) write `.check/` inside submodule checkouts and load multi-namespace imports, which rule 1 forbids. The nudge is host-state-dependent by design: it fires at ~73% reclaimable here, and a clean host legitimately emits nothing (fail-soft).
