# 2026.256.0717 — fix(bed): key the bed-run guard on the user-scoped lock, not the project dir

## Summary

**The duplicate-run guard already existed — and did not cover the measured collision.** It keyed on `.check/<bed>/.lock`, a path relative to the **invoking project directory**, while what two runs of one bed collide on lives in the **user's shared podman store**:

- two runs of the same bed started from two project directories take **different lock files** → the second sees no contention and proceeds;
- the container/volume names it then claims are derived from the bed's **deploy identity** (`charly-check-githubrunner-pod`, from `spec.ContainerName*`) and are user-global → the second run **reclaims the first run's container/volumes instead of testing them**.

### The fix

The image build lock made exactly this move for exactly this reason — opencharly/charly `CHANGELOG/2026.189.0437.md`: *"image build lock is user-scoped on the full ref (cross-project race)"*, where a per-`.build`-dir key produced the same silent multi-writer race in the shared graphroot. **The key belongs to the resource that collides, never to the directory the command happened to run from.**

- **NEW `bed_lock.go`** — `bedRunLockPath(bed)` = `$XDG_CACHE_HOME/charly/locks/bed-<sha8>.lock`, beside the `image-<sha8>.lock` / `localpkg-<sha8>.lock` build locks. **One derivation for both consumers** (R3): the guard and the stopper.
- **`bed_session.go`** — the guard acquires the user-scoped lock. The refusal says *why* (two runs of one bed share the container/volume names of its deploy identity in the podman store, so the second would reclaim the first run's containers and volumes instead of testing them) and hands over the remedy: `charly check stop <bed>`.
- **`stop_cmd.go`** — resolves the SAME path through the helper (previously re-derived project-relative from `cwd`), so the stopper and the runner can no longer disagree across project directories. **Bonus:** `charly check stop <bed>` is now project-independent — it can stop a run started in another checkout, precisely the case the old key could not see.
- **Tests (`bed_lock_test.go`)** — cwd-independence (the old project-relative key fails this assertion), the golden key pin, same-bed contention vs different-bed independence.

No silent stealing: a concurrent second run of the same bed is REFUSED with the reason, not run alongside.

- **Effect on the verdict:** none — the run's last line is `PASS (steps=14)`, the refusal appears both before the run and after its cleanup, and no bed step depends on the vfio mode being restored. No GPU bed was run in this work, and the device was not touched.
