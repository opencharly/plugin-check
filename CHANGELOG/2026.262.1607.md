# 2026.262.1607 — fix(bed): stop the keeper domain after an on_finalize golden capture

## Summary of changes

**RCA + fix: stop the keeper domain after an on_finalize golden capture (the
hanging-golden-lock).**

A bed with `snapshot: {on_finalize: <name>, mode: external, keep_venue: true}` captures a
golden at install finalize, then re-uses it as the shared clone SOURCE for anchored lanes
(`from: <bed>:golden`). The capture created the external snapshot while the **keeper
domain stayed RUNNING on it**, so the keeper held an **exclusive qemu write lock** on
`snapshots/<name>/disk.qcow2`; every clone then failed to open that file as a read-only
backing.

`keep_venue: true` forces `opts.Keep`, which suppressed the teardown's `vm destroy`, so
the runner never released the lock. `docs/golden-vm.md` already required "stop the domain
so the golden is never held exclusively" — the runner never did it.

**Fix.** Add `section 5.3.2`: after the capture, emit `snapshot-stop-keeper`
(`vm stop <entity> --domain <bed-domain>`, idempotent). The venue stays KEPT; only the
running process is released. The capture and the keeper-stop share ONE predicate
(`capturesGolden`) and ONE sequence (`goldenCaptureSteps`).

**Closes / relates to:** none.

**Breaking change + rollback:** none — an added post-capture step. Revert restores the
hang.

FALSE and the new keeper-stop deliberately does not fire there. The changed code path is
not reached, so that bed cannot fail on this change and is not claimed as evidence.
