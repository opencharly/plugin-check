# 2026.243.1616 — fix(bed): repair container DNS at bring-up, which our own teardown breaks

## Summary

**A disposable bed poisons the next bed on the same host, and the damage is host-wide.**

podman destroys the rootless network namespace when the container count reaches zero and
builds a fresh one on the next start — but it does not restart `aardvark-dns`, which keeps
serving the namespace nothing uses. A bed's own `cleanup-members` phase is the thing that most
reliably empties an idle host, so **running a bed to completion is what breaks name resolution
for whatever runs next** — including other sessions' beds.

Nothing looks wrong afterwards:

- the aardvark process is alive
- the bridge is up in the new namespace with the correct gateway
- the zone file is correct and even lists the new containers by name and IP
- `podman network inspect` still reports `dns_enabled=true`

Only the listener is in the wrong namespace. Every `getent hosts <peer>` inside every container
returns empty, surfacing far from the cause as `cannot resolve <name>` in a plan step.

## Observed

A two-member fleet bed paired correctly at 13:00 (`paired 10.89.0.135:9777`). Every run after
it failed at the same step:

```
aardvark-dns           net:[4026534654]      <- still serving here
podman rootless netns  net:[4026533620]      <- everything actually lives here
```

Cross-container resolution was dead for **every** container on the host, not only the bed being
debugged. Hours went into the change under test, the bed's mount configuration, and podman's
overlay store before anyone compared namespaces.

## The fix, and why it belongs here

The bed runner compares the two namespaces before bring-up and repairs a definite mismatch:

1. `SIGKILL` — a stranded aardvark ignores `SIGTERM` (observed)
2. remove the stale pidfile — podman consults it, believes a healthy daemon is running, and
   starts no replacement, so killing alone leaves DNS dead
3. `podman network reload --all`

Idempotent, and a no-op on a healthy host.

**Documenting a manual runbook instead would have been the workaround.** A bed that silently
breaks the next run is not a gate, and expecting operators to notice and hand-fix it puts the
cost on everyone downstream — including people whose runs had nothing to do with the bed that
caused it. The failure is created by our own teardown, so the repair belongs in our own runner.

## How tested

```
$ go build ./... && go test ./...
ok  	github.com/opencharly/plugin-check/candy/plugin-check	24.854s
```

**Four guards**, each pinning something this failure taught:

- **a mismatch triggers repair** — the failure itself
- **the healthy case is left alone** — otherwise every bed run restarts DNS for every container
  on the host, which is worse than the bug
- **incomplete evidence never repairs** — no daemon, an unreadable namespace, or podman not
  answering must not trigger a kill, or a bed breaks a host that was fine
- **`aardvarkPID` never returns the calling process** — it scans `/proc` rather than using
  `pgrep -f`, whose pattern form also matches the caller's own command line. Not hypothetical:
  the same mistake with `pkill -f` during this investigation killed the caller (exit 144). The
  result here is passed to `kill -9`, so a self-match would kill the bed runner mid-run.

**Negative control** — the incomplete-evidence check removed, so any difference repairs:

```
--- FAIL: TestIncompleteEvidenceNeverRepairs
FAIL	github.com/opencharly/plugin-check/candy/plugin-check
```

The decision is split into a pure `containerDNSNeedsRepair(pid, got, want)` so the stranded
case is exercised **without** reproducing it — reproducing it means breaking DNS for every
container on the host, including other people's work.

**Fresh-rebuild bed run WITH the changed runner.** charly was built against this branch
(`go mod edit -replace …/plugin-check`, then `task build:binary`; the binary contains the
repair path — `strings bin/charly | grep 'container DNS: aardvark-dns'` → 1 match), and a
disposable bed run end to end:
