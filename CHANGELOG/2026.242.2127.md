# 2026.242.2127 — fix(diagnostics): a bootloader alpm hook cannot succeed in a pacstrap chroot

## Summary

`charly check run check-omarchy-pacstrap-vm` cannot get past its first step on
`opencharly/distro-omarchy` main:

```
[vm-build] FAIL after 4m30.28s: vm-build exited 0 but its log carries 1 error line(s);
first at line 1387: ERROR: FAT32 boot partition not found. Make sure it is mounted or
configure ESP_PATH in /etc/default/limine.
```

Note `vm-build exited 0` — podman built the disk successfully. It is the bed's
errors-fatal log gate that rejects the run, and correctly so until this line is accounted
for.

### Root cause

Omarchy manages its bootloader through alpm hooks: `limine`, `limine-mkinitcpio-hook` and
`limine-snapper-sync` are hard dependencies of the `omarchy` metapackage, which the VM
entity installs. `80-limine-efi-deploy.hook` therefore fires **during the pacstrap
transaction**, and at that moment

- the target's ESP is not mounted (pacstrap runs against a chroot), and
- `/etc/default/limine` does not exist yet — charly's own bootloader phase writes it
  *after* the package transaction.

So `limine-entry-tool` falls back to its default `ESP_PATH`, finds no FAT32 filesystem
there, and errors. It cannot be configured into succeeding: the tool requires a genuinely
mounted FAT32 partition, which a chroot does not have.

This is the third member of a family charly already ships two allowances for, on this exact
venue — `mkinitcpio-chroot-autodetect-fallback` (no root device in a chroot) and
`pacman-hook-failed-mkinitcpio-recovered` (pacman reporting that hook's nonzero exit). The
third was never added because omarchy is the first distro charly bootstraps whose
bootloader is deployed by a package hook rather than by charly alone.

### Not a regression — measured both ways

The failure reproduces identically on a charly built with plugin-vm **`v0.2026242.812`**
(before the recent pin bump) and with **`v0.2026242.1912`** (after): same message, same log
line 1387, and `charly vm build` exits 0 in both cases.

```
$ charly vm build omarchy-pacstrap-vm          # pre-bump charly
...
Wrote .../omarchy-pacstrap-vm/disk.qcow2 (rootfs sha256=0eadaf0889e71a089c2…)
OLD_EXIT=0
$ grep -n 'FAT32 boot partition not found' oldbuild.log
1387:ERROR: FAT32 boot partition not found. …
```

The bed has been unrunnable on that repo's main since the entity landed; the bed evidence
in the PR that landed it was produced on a tree whose `source.package` did not yet carry
the `omarchy` metapackage.

## Why an allowance rather than a fix elsewhere

Every alternative is worse:

- **Mask the hooks.** The machine images need them intact — that is how a kernel update
  regenerates boot entries on a real Omarchy install.
- **Fake an ESP in the chroot.** Mounting a FAT32 that is not the guest's real ESP purely
  to quiet a hook.
- **Drop the metapackage.** Then the guest is not Omarchy: `pacstrap.base_package` is a
  minimal bootstrap set and the result reports `ID=arch`.

## Conditional, like every error-tier allowance

`RecoveredBy: ^Updated: /boot/limine\.conf$` — charly's bootloader phase doing the job
properly against the **real, mounted** ESP later in the same build. Observed live: the
hook errors at line 1387, then

```
1438  Boot000F* Omarchy  HD(1,GPT,c950b917,…)/\EFI\BOOT\BOOTX64.EFI
1497  Copied: /tmp/limine-mkinitcpio.X/linux.efi -> /boot/EFI/Linux/omarchy_linux.efi
1498  Updated: /boot/limine.conf
```

If `/boot/limine.conf` is never written the allowance does not claim the line and the step
still fails — the difference between a chroot artifact and a genuinely broken bootloader
install, and the reason this is not a blanket suppression.

The pattern tolerates limine's **trailing space** after the final period. Without it the
allowance would silently never match and every omarchy pacstrap build would keep failing; a
test asserts it.
