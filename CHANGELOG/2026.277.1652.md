# 2026.277.1652 — fix(check): record a bed verdict on every exit path — return, error, panic and signal (#779)

## Summary

A `charly check run` bed could end with **no `summary.yml` at all**. `writeBedSummary` had exactly three call sites — the prereq-skip arm, the `fail()` tail and the success tail — so any death that was not one of those three left a run dir holding per-step logs and **no verdict**. Such a run is indistinguishable from a run that is merely slow, and there is nothing in the dir to diagnose from. That is **opencharly/charly#779**, and it is why the bed runs behind that issue could not be reproduced.

Two mechanisms, because the exit paths are **disjoint**:

1. **`recordBedVerdict` — ONE deferred writer** in `runCheckBed`, covering every path that UNWINDS: an early return, a returned error, a panic. It takes the named results by pointer so it sees what the function actually returned, and re-panics after recording — recording and crash semantics stay separate. Deferring makes the record *more* complete, not less: it runs last, after `bedTeardown` and the instrument finalizer, so the summary describes the state the run ended in. The three ad-hoc `writeBedSummary` call sites are **removed in this same change** — no dual path.
2. **`writeStopped` via `proc.RegisterShutdownHook`** — the signal path, which a `defer` structurally CANNOT cover: `InstallSignalHandler` runs its registered cleanups and shutdown hooks and then re-raises with the **default disposition** (`spec/proc/cleanup.go:130-142`), so nothing unwinds and no deferred function runs. The hook synthesizes the verdict from **primitives only** — never the live `*bedRunResult`, whose `Step` slice the main goroutine is appending to while the hook runs on the signal goroutine — and writes it **once**. `endBedVerdict` disarms it so a later process exit cannot rewrite a finished run.

The record also becomes diagnosable, which is the second half of #779's complaint:

- `driver` / `driver_size` / `driver_mtime` — from `os.Executable()` + `os.Stat`, **no subprocess** (this value is read on the signal path, where spawning a child would be both unbounded and unsafe). A dev/worktree build and an installed `/usr/bin/charly` are otherwise indistinguishable after the fact.
- `stopped` / `stopped_reason` / `in_flight_step` — emitted **only** when the run did not reach one of its own exit paths, so their absence on a normal run is itself the statement that the run finished normally.
- `skip_reason` — a prereq skip was previously explainable only from the returned error; the run dir itself could not say why nothing ran.

**Serialization (commit `d0fea6e`).** Both writers go through `writeVerdictOnce`, which holds the state lock **across** the file write, so "first writer wins" is an invariant rather than a hope. Without it there is a real, if narrow, race: a signal delivered while the main goroutine was already unwinding would let the hook overwrite a truthful, complete verdict with a stopped-state one.

**Block 2 of the BLOCK — the panic path's `in_flight_step` was dead in production, and the test masked it (commit `da10206`).** The finding was correct on both halves, and this head fixes both:

- The step closures clear the in-flight step with `defer state.leaveStep()`, and **a defer runs while a panic unwinds** — so by the time the panic arm of the writer read the state, the step was already `""`, and `writeBedSummary` omits an empty `in_flight_step`. The fix tracks the last step **entered** separately from the current one (`lastStep`, never cleared) and reads it through `snapshotStepAfterUnwind`, which prefers the live step and falls back to it. `snapshotStep` is unchanged for the signal path, which records and then re-raises **without unwinding** (`spec/proc/cleanup.go:130-142`).
- The panic subtest now reproduces the **production frame** — the step is entered inside a closure that publishes itself, defers its own clear, and panics, with the recover in an enclosing function calling `recordBedVerdict` — so the real unwind happens and `in_flight_step: check-live` is load-bearing. The previous revision called `enterStep` and the writer directly with no unwind between them, which is exactly what certified the shape I imagined rather than the one the runtime produces.

**R1, self-caught in the same head:** the `lastStep` comment cited `TestBedVerdictNamesTheStepThatPanicked`, a test name that **does not exist** in this tree (`grep` finds the citation and no such function). It now names the real assertion — the `panic` subtest of `TestBedVerdictWrittenOnEveryUnwindingExit`.

**Stated bounds.** SIGKILL is uncatchable (`spec/proc/cleanup.go:126-129`; this plugin's own `stop_cmd.go` escalates to it), so a SIGKILLed run still cannot record a verdict. This change makes TERM/INT/HUP, panic and every returning path diagnosable — not SIGKILL. That is a stated bound, not an oversight.

Closes opencharly/charly#779. Relates to opencharly/charly#775 — the tracked issue for exactly this gate gap, whose scope item 1 is what made the R10 run below possible.

### The bed, and why this is the right one

`check-local` is the R10 witness this repo's `AGENTS.md` names (*"the disposable `check-local` bed (in `opencharly/charly`), run to a fresh `charly update` plus a short iterate"*). It is only ever run **inside** the disposable guest: it applies `check-local-layer` to `host: local`, so running it bare on the operator's workstation would write `/etc/check-local-marker` onto a real machine. The host-side entry point is the outer bed **`check-local-vm`** (`opencharly/charly` root `charly.yml`: `vm: {from: eval-host-vm, disposable: true, cpu: 2, ram: 2G, lifecycle: dev}`), whose authored plan step `guest-as-host-check-local` delivers the pruned `check-local` project into the guest project dir and runs `charly --host <vm> check run check-local` **inside the guest**. The guest's charly is the **host's own binary** — the `charly-dev` candy welds `copy: bin/charly` — so the nested bed is driven by exactly the build below.
