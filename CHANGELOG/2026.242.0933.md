# 2026.242.0933 — fix(check): allowlist the benign grub-probe-on-fuse-overlayfs error in image builds

## Summary

A debian-coder image build emits `/usr/sbin/grub-probe: error: failed to get canonical path of …` — a benign Debian-in-container error: package postinsts (grub-common, mdadm) run grub-probe during the build, and the container root is an overlay grub-probe cannot canonicalize. The postinst continues, the build completes and the image is tagged (exit 0), but the error-tier gate flags the line as fatal.

Adds a CONDITIONAL error-tier allowlist entry, `grub-probe-fuse-overlayfs-recovered`: the line is exempt only when the same log proves the image was tagged (`Successfully tagged `). If the build never tags, the entry does not claim the line and the step still fails — the conditional invariant the error tier requires.

**The first version of this entry did not work, and the bed run is what caught it.** The pattern was anchored on `of '...'`. The line the build actually emits is, byte-for-byte (`od -c`):

```
/usr/sbin/grub-probe: error: failed to get canonical path of `overlay'.\r\n
                                                             ^                ^^^^
                                                             U+0060 backtick   CRLF
```

Three things differ from what the pattern assumed:

1. **GNU quoting opens with a BACKTICK** (U+0060) and closes with a straight apostrophe. A pattern anchored on `'...'` matches nothing.
2. **The subject is `overlay`** — the storage driver — not `fuse-overlayfs` as the earlier body claimed.
3. **The line ends CRLF**, so a bare `$` anchor is at the mercy of the trailing `\r`.

Fixed: the delimiter is `[`']`, the trailing `\r` is tolerated, and the regression test now carries the captured bytes instead of a hand-typed approximation.

## How tested

**Reproducing the line at all required a COLD store.** The first attempt — a full `check-debian-coder-pod` bed on this machine's warm store — built at `cache=330/359`, so the Debian postinsts never re-ran and the log contained **zero** grub-probe lines:

```
[image-build] PASS after 1m22.139s [allowlisted=1 cache=330/359]
$ grep -c 'grub-probe' image-build.log
0
```

So the build was re-run cold, on a wiped isolated store (`CONTAINERS_STORAGE_CONF` with its own graphroot, `podman system reset --force` between runs):

```
$ charly box build debian-coder          # cold store, 212 steps
$ grep -c 'grub-probe' colddeb.log
1
$ grep -c 'Successfully tagged' colddeb.log
3
$ grep -m1 'grub-probe' colddeb.log
/usr/sbin/grub-probe: error: failed to get canonical path of `overlay'.
Successfully tagged ghcr.io/opencharly/debian-coder:2026.242.0853
```

The error line and the `Successfully tagged` recovery, in the same log — which is exactly the pairing the entry claims.

**The old pattern against those real bytes** — fed through the actual scanner, not reasoned about:

```
$ go test -run TestGrubProbe_RealCapturedLine -v .
    grub_realline_test.go:15: errors=1 warnings=0 allowlisted=0
    the real captured grub-probe line is NOT claimed by the allowlist
--- FAIL: TestGrubProbe_RealCapturedLine
```

`errors=1, allowlisted=0` — the step would still have failed. The entry was inert.

**After the fix**, including the conditional half:

```
$ go test -run TestGrubProbe -v .
--- PASS: TestGrubProbeFuseOverlayfsIsConditional
    --- PASS: .../recovered_by_the_image_tag
    --- PASS: .../no_recovery_is_fatal
    --- PASS: .../unrelated_error_is_not_exempted_by_a_tag
--- PASS: TestGrubProbe_RealCapturedLine_Recovered            (errors=0 allowlisted=1)
--- PASS: TestGrubProbe_RealCapturedLine_NoRecoveryIsFatal    (errors=1, still fatal)
ok  	github.com/opencharly/plugin-check/candy/plugin-check	0.004s

$ go test ./...
ok  	github.com/opencharly/plugin-check/candy/plugin-check	0.006s
?   	github.com/opencharly/plugin-check/candy/plugin-check/cmd/serve	[no test files]
```

`TestGrubProbe_RealCapturedLine_NoRecoveryIsFatal` is the negative control on the real bytes: strip the `Successfully tagged` line and the same input goes back to `errors=1` and fails the step, so widening the delimiter did not turn the entry unconditional.

## The `check-live` failures this run surfaced — root-caused, routed to opencharly/charly#480

The earlier revision of this body recorded these without a cause. That was the wrong disposition; here is the RCA.

The warm-store `check-debian-coder-pod` run failed later at `check-live` on three checks shipped by the `charly-mcp` candy (243 others pass):

```
FAIL  check mcp=call  [mcp-charly-call-version]      (tool version reported an error)
FAIL  check mcp=call  [mcp-charly-call-list-boxes]   (tool box.list.boxes reported an error)
FAIL  check command=charly status --json  [status-shows-pod]  exit=1
```

Driving the venue's MCP endpoint directly (real session handshake) gets the tool's own error instead of the truncated one:

```
charly: cannot resolve --repo "default": resolving default branch for github.com/opencharly/charly:
git ls-remote --symref https://github.com/opencharly/charly.git HEAD: exit status 128
```

The chain: the pod's cwd (`/home/user`) holds no `charly.yml`, so charly falls back to `--repo default` — the **remote** repo — and resolving it runs `git ls-remote` against github.com *from inside the venue*. That needs in-venue DNS, and there is none:

```
$ podman exec charly-check-debian-coder-pod git ls-remote --symref https://github.com/opencharly/charly.git HEAD
fatal: unable to access '…': Could not resolve host: github.com
```

**It is the network, not this change, not the bed, and not my checkout** — a fresh unrelated container on the same podman network reproduces it with no charly bed involved:

```
$ podman run --rm --network charly <any-image> sh -c 'getent hosts github.com && echo OK || echo FAILS'
nameserver 10.89.0.1
DNS FAILS

$ podman run --rm <same-image> sh -c 'getent hosts github.com >/dev/null && echo "DNS OK"'   # default network
nameserver 169.254.1.1
DNS OK
```

Narrowed to DNS specifically rather than egress, with the resolver alive:

```
$ pgrep -x aardvark-dns  ->  RUNNING
$ podman network inspect charly … dns_enabled=true internal=false subnets=10.89.0.0/24
$ podman run --rm --network charly <img> curl -o /dev/null -w '%{http_code}' https://1.1.1.1   ->  301
```

So containers on the `charly` bridge have working egress and a live `aardvark-dns`, but upstream name resolution does not return on this host (its resolver list includes a Tailscale stub, per the `armadillo-quail.ts.net` search domain).

Two separable problems, both in **opencharly/charly#480**: the host-side DNS forwarding (why it fails here), and the check design — `version`, `box.list.boxes` and `status-shows-pod` reach GitHub from inside a venue only because no project is mounted and `--repo default` is the fallback, which makes them fail in any DNS- or egress-restricted bed for reasons unrelated to what they test.

**Why this does not qualify the entry below.** It is in `check-live`; this entry governs `image-build` diagnostics. The `image-build` step passed in that same run, and the control experiment above reproduces the DNS failure with no charly bed at all.
