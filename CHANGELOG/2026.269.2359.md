# 2026.269.2359 — fix(check): bound roster lanes by host memory (with the low-RAM floor)

## Summary

Bound a `check-roster`'s concurrency by **host memory**, so "run all beds" cannot
OOM-kill the host mid-roster (plan RCA-I). `clampRosterLanes(requested, bedCount)`
treats the authored `lanes:` as an upper bound, capped by `runtime.NumCPU()`, the bed
count, and the host memory ceiling (`rosterMemCeiling`, MemTotal / 6 GiB). A readable
low-RAM host floors the ceiling to 1, so it is bounded rather than treated as
"unknown" and skipped.

### RCA (8-step, measured)

**Unexpected.** A 128-bed `charly check run check-all-beds` vanished mid-run with no
error; `ps` showed the parent at ~13 GB RSS, and the user cgroup
`memory.events.oom_kill` reached 14 (`memory.peak` 59 GB on a 61 GB host).

**Mechanism.** The root `charly.yml` authored `lanes: 16`; each lane can hold a
podman buildah tree + a VM qcow2 copy. At 16 lanes the concurrent working set
exceeds host RAM, so the kernel OOM-kills the roster.

**Evidence (measured).**

```
lanes: 16 -> memory.peak 59 GB, oom_kill 14  (roster killed)
lanes:  2 -> used 9->15 GB steady over 17 min, roster alive, beds completing
```

Memory scales with **concurrency (lanes)**, not total bed count.

`clampRosterLanes` is split into a host-injected core
`clampRosterLanesTo(requested, bedCount, cpus, memCeil)` (deterministic on any host)
and the readable-vs-unknown `rosterMemCeiling(total, readable)`:
- `TestClampRosterLanesTo` — memory/CPU/bed/unknown-memory cases (the memory case
  fails if the memory branch is removed).
- `TestClampRosterLanes_HostBounds` — host wiring (`<=` bound, `>= 1`).
- `TestRosterMemCeiling` — a readable 4 GiB host floors the ceiling to **1** (not 0);
  unreadable/absent meminfo stays 0 (no bound). Fails if the floor is removed.

### Live clamp — the MEMORY bound is the binding constraint, and the roster SURVIVES

On this 61 GB / 16-CPU host `MemTotal/6 GiB = 10`, so a 14-bed roster with
`NumCPU 16` makes the memory ceiling the unique binding bound (`min(16,16,14,10)=10`).
The roster is `roster-memproof`, selecting the 14 `disposable: true` beds
`charly.fedora.check-*-pod`, run on a FRESH rebuild of this tree:

```
$ charly version
2026.269.2058                    # == the HEAD commit's CalVer (charly/version.go ComputeCalVerAt)

$ charly -C . check run roster-memproof
charly check run roster-memproof: roster — 14 bed(s) selected, 0 refused (host-local)
charly check run roster-memproof: lanes 16 -> 10 (host-memory-aware cap)
```

The 14 beds then ran at those 10 memory-bound lanes and **the host survived** (no
OOM, parent RSS bounded) — the exact outcome lanes:16 did NOT produce.

### The beds' `image-build` failures are a NAMED defect (charly#699), not this clamp

With the clamp in force, the selected beds abort at `image-build` — but NOT at the
build itself: the SAME image builds green directly (`charly box build
charly.fedora.fedora-test` → exit 0). Under 10 concurrent builds the plugin host
starves and the production no-progress watchdog false-fires:

```
charly: error: command "build": rendering Containerfiles: generating Containerfile for charly.fedora.check-pod:
  InvokeProvider builder:examplebuilder op=resolve: ... made no host-visible progress within the no-progress
  window (hung plugin — the peer runs no host work)
```

Root cause: the plugin no-progress watchdog (`charly/charly/plugin_activity.go`)
trips on host starvature under concurrent plugin invocations — the SAME starvation
class already documented in `charly/CHANGELOG/2026.269.2034.md` for a test
("on a loaded host … that goroutine can be starved past [the window], so the window
expires and the test false-fails a call that is plainly progressing"). Routed to the
named batch **opencharly/charly#699** (fix the production watchdog), which owns both
this and the roster's bed non-completion.
