# 2026.288.1336 — fix(bed): the VM path's deploy carries the run tag, as the pod path already does

## Summary

`charly deploy add` with **no `--tag`** resolves *"the newest local CalVer"* of the box, so a box with more than one local build can have its pod or VM run an artifact this run did not build. The bed runner had grown this pin by hand, at ONE call site — the pod arm (`addArgs = withRunTag(addArgs, d.ImageTag)`), whose sibling `configStartArgs(…, d.ImageTag, …)` covered the other half. **The VM path had no tag at any of its three sites.**

**This PR makes the two paths symmetric, and claims exactly that.** The pin now lives where every deploy already passes — `bedAdd` — as a separate, TYPED parameter:

```go
func bedAdd(refs []string, tag string) []string { … return withRunTag(append([]string{"deploy", "add"}, append(args, "--dev-local-pkg")...), tag) }
```

All eight call sites pass `d.ImageTag` (VM root, VM host-rooted children, the in-place local arm, the pod arm), and the pod path's hand-written `withRunTag` is deleted as redundant — one home, so the next caller cannot miss it (R2).

**What this PR does NOT claim, stated first rather than defensively: that carrying the tag is sufficient to pin the artifact.** It is not, and the record already measures that: a pod bed that *already* passed `--tag <run calver>` still ran a base image baking `0.48.1` while the run's own build bakes `0.51.0` and its own `check box` step asserted `0.51.0` and passed (one run, two steps apart — `opencharly/plugin-check#115`). **Symmetry is what this change buys; pinning is what `#115` must still establish**, and its `HANDING OVER` names the one measurement that decides it (which field `--tag` matches: the image's CalVer tag or its `ai.opencharly.version` label) and the three candidates that separates. An earlier revision of this body asserted the guarantee in its title; that claim was refuted by this very measurement and is withdrawn.

**Why the signature is the way it is, because the first attempt proves the point:** I first made the tag a variadic FIRST argument (`bedAdd(tag string, args ...string)`), and the existing test immediately showed what that costs — a caller passing a ref where the tag belongs produced `--tag openclaw.check-openclaw-pod`, i.e. **a deploy pinned to the wrong thing, the same defect class this change exists to remove.** The suite caught it (`TestBedAddConvertsTheRosterAddress` FAILED) and the type now makes it unrepresentable.

## Filed issues

* **`opencharly/plugin-check#116`** — *a bed whose live phase does not assert WHICH artifact it deployed, so its green is evidence about some image* (open). Genuinely separable from this change by R1's test, and now correctly classified as such because the claim no longer depends on it. It names the mechanism (`DeployRecord.ResolvedImage` + `runTaggedImageRef`) and records what this round learned about reaching it: the bed runner has **no executor seam** (`run_cmd.go` re-enters the CLI rather than threading one — `bed_ephemeral_timers.go` reaches the deploy overlay through the session's executor, not the runner's), and `charly deploy add --dry-run --format json` emits the **InstallPlan**, not the resolved image reference — so the guard needs either an executor on the runner path or a CLI verb that names the resolved artifact. A successor should not have to rediscover that.
* **`opencharly/plugin-check#115`** — the parent defect, with a `HANDING OVER` naming the one measurement that decides its fix and the three candidates it separates. This PR does not close it: the pod path was already tagged and still ran a stale base, so the pod-side cause is that row's. `opencharly/plugin-crabbox#8` therefore stays held, its stock-plugin control the proof that its red is foreign.
