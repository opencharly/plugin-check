## Summary

**Successor to the auto-closed `opencharly/plugin-check#108`** (Part II #7: a validator-closed PR continues in a new PR from a fresh branch). **Lineage: `#92` → `#102` → `#106` → `#107` → `#108` → this PR.** Same change, and now with the change-class gate GREEN.

**One bug, one conversion.** A namespaced bed is addressed `<ns>.<name>` by a roster, but its deploy is created under the deploy key `<ns>/<name>`. `spec.ContainerName` is faithful to the ref it is handed — it maps `"/"` to `"-"` and nothing else — so the two spellings name different containers:

```
charly config openclaw.check-openclaw-pod  ->  charly-openclaw.check-openclaw-pod   (roster address)
charly config openclaw/check-openclaw-pod  ->  charly-openclaw-check-openclaw-pod   (deploy key)
```

Three consequences followed from mixing them, all measured:

1. **five lookups resolved a name the deploy had not created** — `venue.go`, `live_gather.go`, `feature_run_gather.go`, `members.go`, `instrument.go` — so a live probe reported `container … is not running` **for a running container** (`sdk/deploykit/container_resolve.go:40`).
2. **`deploy add` was handed the roster address**, so the deploy resolver derived a bare NAMESPACE and `FilterBox` rejected it: `unknown box "openclaw"` (`sdk/deploykit/graph.go:312`) — filed as **`opencharly/plugin-build#28`**.
3. **the container the deploy created was unreachable by every path that asked for it by the other spelling.**

**The change:** one `deployKeyForBed` conversion, reached from every site — a shared `resolveBedContainer` helper at all five lookups, and the same conversion inside `bedAdd` (eight callers, all passing a roster address, so converting inside it makes a ninth caller impossible to miss — R2). Remote refs are excluded: `spec.ResolveBoxName` resolves those by parsing, not namespace splitting.

**Also in this diff, the predecessor's third change:** `resolve_endpoint.go` / `venueIsInspectable` / `venue_inspectable_test.go`. *A dot in the requested name does not make a venue un-inspectable: `resolveCheckVenue`'s dotted branch returns a `Kind: container` venue for a root-namespaced deploy, so testing the NAME for a dot **discarded a venue the resolver had just resolved**.* **Two causes, one message, and they are not the same defect:** that guard discarded a resolved venue; the five lookups computed a different container name than the deploy created. *Both surfaced as "is not running" for a running container, and both are fixed.*
