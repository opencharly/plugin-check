# 2026.250.0724 — feat(check): thread the deployment's mcp_provide into the check env for VM venues (P4 substrate-neutral mcp: verb resolution)

## Summary

P4 (substrate-neutral mcp_provide + mcp: verb resolution, plan §3.10): thread the deployment's `mcp_provide` declarations into the check env a VM venue's out-of-process verb dispatch marshals.

A kind:vm entity declares its MCP servers (`mcp_provide: [{name, url, transport}]`, spec #Vm · merged v0.2026250.709), but a VM has **no podman-inspectable OCI label** — the `ai.opencharly.mcp_provide` label exists only on container images — so the substrate-neutral `mcp:` check verb cannot resolve the endpoint on a VM the way it does on a container. `spec.CheckEnv` now carries `mcp_provide` (#CheckEnv, spec v0.2026250.709) for exactly this: the check env the host/driver marshals into every out-of-process verb dispatch carries the declaration itself.

**This PR (the plugin-check side of the P4 split):**
- **spec re-pin**: `github.com/opencharly/spec` v0.2026250.523 → **v0.2026250.709** (`go mod tidy`, go.sum updated). `sdk` stays v0.2026250.527.
- **Gather-side seeding**: `pluginCheckLiveVM` (live_gather.go) and `pluginCheckRunFeatureLiveVM` (feature_run_gather.go) seed the constructor `spec.CheckEnv` with `MCPProvide: pluginResolveVmMcpProvide(rp, vmName)` — a new helper that reads the vm template's **raw authored body** (`rp.Templates.VM`, the same source `pluginResolveVmSpec` decodes; same pattern as checkproject.go's include-plan vm decode into `spec.Vm`). `spec.ResolvedVm`/vmshared.VmSpec — the resolved envelope this package consumes — mirrors #Vm's fields explicitly and does NOT carry `mcp_provide` (spec-side mirror drift, see the routed note below); the raw body is the authoritative authored deployment metadata.
- **Resolver threading**: `pluginVerbResolver` gains `mcpProvide []spec.CandyMCPProvide`, captured in `newPluginCheckRunner` from `env.MCPProvide` (plugin_runner.go). `pluginSnapshotCheckEnv` — the plugin-side, field-for-field mirror of charly/provider_checkenv.go's `snapshotCheckEnv` — now takes the declarations and threads `ce.MCPProvide` when the venue kind is **not** `container` (VM/host venues: no OCI label; container venues keep resolving from their image label, so the env never carries it there). RunVerb's FRESH per-call snapshot (the value actually marshalled into the wire envelope for every out-of-process verb dispatch) therefore carries the VM's MCP servers on every dispatch, not just the defensive construction-time fallback env.

**Charly-side producer note (the other half of the P4 split, lives in opencharly/charly):** the host's `snapshotCheckEnv` (provider_checkenv.go) must in turn populate `ce.MCPProvide` from the deployment's box/vm metadata for host-driven runs (its CheckContext carrier is the deployment-metadata holder; this plugin's mirror reads the same deployment metadata off the resolved project envelope). That change rides the charly consumer re-pin PR of this wave (spec 709) — the named P4 batch item on the charly row.

**Spec-side mirror-drift routing (R2 — the `#ResolvedVm` gap has a NAMED batch):** `#ResolvedVm` (spec/schema/vm.cue) is a hand-written field mirror of `#Vm` and omits the P4 `mcp_provide` field, so the RESOLVED vm envelope drops it. Not a plugin-check blocker — the raw template body is the canonical authored source and is what this PR reads. The fix is routed to the **P4 substrate-neutral wave's spec row (opencharly/spec)**: add `mcp_provide` to `#ResolvedVm` + `cue:gen` + extend `vm_mcp_provide_test.go` with the resolved-envelope parse case — the sibling spec PR to this one, before the charly consumer re-pin.
