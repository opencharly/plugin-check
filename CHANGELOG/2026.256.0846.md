# 2026.256.0846 — fix(check): allowlist the pacman container post-transaction hook wrapper error

## Summary

**What changed.** Three edits, all in `candy/plugin-check/bed_diagnostics.go`, plus tests:

1. **`pacman-post-transaction-hook-container-systemd`** — a narrow, CONDITIONAL allowlist entry for the in-container pacman post-transaction hook wrapper error the scanner scored FATAL (batch `check-scanner-container-hook-allowlist`).
2. **`podman-nested-rootfs-not-shared-mount`** — a narrow, CONDITIONAL allowlist entry for the podman logrus advisory an IN-CONTAINER nested rootless podman prints.
3. **Claim resolution by proof instead of table order** (`allowanceClaiming`) — several entries can match one line, so the gate walks the matching entries and returns the first whose OWN `RecoveredBy` proof holds in that step log, instead of letting the first pattern match shadow a later entry whose proof is the one present.

**The emitter, root-caused (R1).** pacman reports a post-transaction HOOK that exits nonzero as the generic `error: command failed to execute correctly`. In these builds exactly one hook does that: **`36-systemd-modules-load.hook`** (shipped by `systemd`), whose Trigger is `usr/lib/modules-load.d/*.conf` and whose Exec is `/usr/bin/systemctl --system restart systemd-modules-load.service`. The triggering file is installed by **`cdrtools`** (`/usr/lib/modules-load.d/cdrecord.conf`), a `DEPENDS` of the **charly** Arch package: the hook runs in the transaction that installs charly, its `systemctl` refuses (`System has not been booted with systemd as init system (PID 1). Can't operate.` then `Failed to connect to system scope bus via local transport: Host is down`), and pacman prints the wrapper error — while the SAME log ends with the image successfully tagged.

**The trigger, isolated — a controlled reproduction with no charly and no image build involved:**

**Why the hook wrapper error is a false positive, not a swallowed failure.** pacman reports EVERY failing post-transaction hook as the same generic `error: command failed to execute correctly`. Inside a container build the modules-load hook calls systemd, systemd refuses, and the hook's nonzero exit becomes that wrapper error — while the SAME log ends with the image successfully tagged. The entry is CONDITIONAL: it claims the wrapper error only in its own severity tier AND only when the SAME step log carries systemd's own container-init refusal — the sentence that names the cause. A real pacman failure (`failed to commit transaction`) and an unexplained hook failure both stay fatal, pinned by tests.

**Why the shared-mount advisory is container-inherent, not a swallowed failure.** The host is not the source: `findmnt -no PROPAGATION /` reports `shared`, and a host-side podman run prints no such line. The emitter is podman itself — its binary carries the format string `%q is not a shared mount, this could cause issues or missing mounts with rootless containers` — and the line lands inside the build's own RUN step, where the OCI runtime has mounted the rootfs MS_PRIVATE by construction, followed in the same log by the pull completing and the image being tagged.

**The entries' boundaries** — every row is a test.

| entry | case | expected |
| --- | --- | --- |
| `pacman-post-transaction-hook-container-systemd` | wrapper error + systemd's container refusal in the same step log | claimed |
| `pacman-post-transaction-hook-container-systemd` | wrapper error without the refusal (e.g. a real `failed to commit transaction`) | still fatal |
| `podman-nested-rootfs-not-shared-mount` | advisory + the same step log tags the image | claimed by `podman-nested-rootfs-not-shared-mount` |
| `podman-nested-rootfs-not-shared-mount` | advisory in a build that never tags | still a warning |
| `podman-nested-rootfs-not-shared-mount` | any OTHER podman logrus warning, tag present | untouched |

## Block 3 — the log-scoped proof: FIXED in this head (`f9dbb2b`)

The review was right, and the previous revision had only named the gap instead of closing it: `allowanceRecovered` asked whether the `RecoveredBy` pattern matched SOMEWHERE in the step log (`re.MatchString(log)`), so once the modules-load chain was present, EVERY `^error: (command failed to execute correctly)$` line in that log was discharged — including a SECOND post-transaction hook failing in the same pacman transaction. pacman prints that one wrapper wording for every failing hook, so the entry's own prose ("a wrapper error belonging to a DIFFERENT failing hook stays fatal even in a log where the modules-load hook is also refused") was not yet what the code did.

**The fix — the proof is now LINE-BOUND.** `diagnosticAllowance` gains `ProofEndsOnLine`: when set, the proof's match must END ON the line being claimed, not merely appear in the log (`re.FindStringIndex` → the match's end line must equal the claimed line). It is set on the container-systemd entry, whose chain TERMINATES IN the wrapper error it names. Entries whose proof is a SEPARATE recovery line (mkinitcpio's success line, dnf's transaction-completion line) correctly leave it off — their proof legitimately sits at another line. `allowanceRecovered`/`allowanceClaiming` now take the 1-based line index `scanStepDiagnostics` already computes; the entry's comment and `Why` state the line binding.

**The boundary is pinned by a test that FAILS without the fix (R7).** New subtest *"a SECOND hook's wrapper error in the same log stays fatal"*: the captured modules-load chain is present AND a second hook's identically-worded wrapper error follows in the same step. Expected: the chain's own line is claimed, the second is counted, the step fails.
