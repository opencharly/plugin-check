# 2026.277.2313 — fix(bed-runner): identify the bed driver by version and mirror the runner stderr into the run dir

## Summary

A `charly check run` could end **without a verdict**, and the run dir could not say why (`opencharly/charly#779`). The verdict-on-every-exit-path half landed in **#76** (merged, `410bd9e`); **this PR is the remainder** — the other two gaps #779 diagnosed. Landing it completes the issue; the issue itself is closed by hand after the merge, because GitHub does not honour a cross-repo closing keyword (see the note at the end of this body).

Both changes are to the bed runner in `candy/plugin-check/`. Neither changes any bed's steps, semantics or pass/fail criteria; they change what a run dir **records**.

### 1. The driver is identified by VALUE, not only by artifact (`#779` item 2, the version half)

`summary.yml` already carried `driver:` (path), `driver_size:` and `driver_mtime:` — from #76. Those three say **which file** ran the bed. None of them says **which build**, and the string a bug report actually quotes is `charly version`. The R10 excerpt below is the real summary this PR produces.

`bed_verdict.go` gains `bedDriver.Version` and three small functions:

- **`charlyBuildVersion()`** reads the running binary's identity out of its own `debug.ReadBuildInfo()`. The plugin cannot import charly's main package, and the CalVer reaches a plugin by no env var and no exported constant — it is stamped in by `scripts/bootstrap-charly.sh` as `-ldflags "-X main.BuildCalVer=<calver>"` (`scripts/bootstrap-charly.sh:95`), which is what `charly version` reports (`CharlyVersion()`, `charly/version.go:29`, reading the `BuildCalVer` var declared at `charly/version.go:21`). Reading build info is **in-process and bounded**, which matters because this value is also read on the *signal* path, where spawning a child would be neither.
- **`buildVersionFrom()`** is the decision, split out so it is testable against real `debug.BuildSetting` values — the live read can only ever observe *this* binary's settings, so a test calling `charlyBuildVersion()` alone could not exercise the stamped case at all (that is a measured limitation, pinned by `TestCharlyBuildVersionOnTheRunningBinary`).
- **`buildCalVerFromLDFlags()`** extracts the stamp from the recorded flag list by prefix, because the stamp may sit beside other `-X` assignments.

`Main.Version` is deliberately **not** used as the primary source: for a build stamped this way it is `"(devel)"` (measured on a real bootstrap-form build). It is used only as a fallback, and an unstamped build reports `unknown` — which is `CharlyVersion()`'s own word for one.

### 2. The runner's stderr is mirrored into the run dir (`#779` item 3)

New file `bed_stderr.go`. `bedStderrCapture` **tees fd 2** into `<run>/runner.stderr.log`, and `summary.yml` references it exactly as it already references `evidence.yml`:

```
runner_stderr: runner.stderr.log
```

Three details are load-bearing, and each is a measured finding rather than a preference:

- **It captures fd 2, not the `os.Stderr` variable.** The Go runtime writes `panic:`, `fatal error:` and its own stack trace **straight to fd 2**, bypassing the variable entirely. Reassigning `os.Stderr` would have looked correct and captured nothing on exactly the path #779 is about.
- **`close()` restores fd 2 *before* closing the pipe's write end, and the drain is bounded.** fd 2 *is* a duplicate of the pipe's write end, so closing the write end first leaves the pipe open by one reference and the reader never sees EOF. I hit this as an **unexplained 600 s package-timeout FAIL** on the first full-suite run; with the order fixed it fails in 2 s with a named cause. The drain is bounded (`bedStderrDrainGrace`) because a process that inherited fd 2 — and a bed spawns containers and VMs — holds its own reference, and `close` runs *before* teardown. Past the grace the truncation is **recorded in the run dir** and the descriptors are deliberately left open: freeing the number under a blocked read could land a later write in an unrelated file, which is worse than a retained descriptor in a dying process.
- **The defer order is the mechanism.** `runCheckBed`'s deferred writer is declared **last** so it runs **first**, while the capture is live — a recovered panic's stack must reach the file through `RecordPanic`, because the runtime prints its own copy only *after* every deferred function has run, by which time `close` has already restored fd 2. That writer is a **named** function, `bedRunGuard`, rather than an inline closure, for one reason: the bed run and its test then call the *same* function, so the recover→`RecordPanic` hand-off cannot be deleted from production while a test-local copy of the line keeps the suite green.

**Bounds, stated plainly rather than implied:** the mirror does not capture a panic stack that the runtime prints after unwinding (that is what `RecordPanic` is for); it cannot capture bytes written after a `SIGKILL`; and the drain is bounded as above.
