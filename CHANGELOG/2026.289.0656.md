## Summary


The bed-runner's venue-readiness wait had **neither a deadline nor a log line on the VM path** — which is why `charly check run` could sit between `[vm-create] PASS` and `[deploy-add] START` with no timeout, no error, and no statement of where it was.

**The hop, from the code the log lines come from:**

```
bed_run.go  step("vm-create", ...)   -> emits [vm-create] PASS
bed_run.go  waitReady()              -> ** emitted NOTHING ** (not wrapped in phase(...))
bed_run.go  step("deploy-add", ...)  -> would emit [deploy-add] START
```

*and `waitReady`'s VM arm called `specexec.WaitForVmSshReady(d.BedDomain)` with **no bound at all**.* **A `waitReady()` that never returns produces precisely the reported symptom — which is why the reporter measured a rate across six runs rather than reading one line.**

## R2 — a prior RCA diagnosed this class and fixed only its sibling

**`bed_readiness.go`'s own comment on `rebuildReadyDeadline` records the earlier finding, verbatim:**

> *"…a TOTAL deadline, so a lease-less boot becomes a named, time-bounded failure instead of **the silent 30-minute cap-only stall**; the container arm keeps the shared self-bounding gate (WaitForContainerReady's 90-second no-progress watchdog…) — **the RCA's stall is VM-only**."*

***So the rebuild wait got both remedies (`waitRebuildReady → waitVenueReady`, and the `phase()` logger added for `#779`'s "unattributed gap"). The INITIAL wait — and four other readiness hops with the same mechanism — were left as they were. That is R2's duplication failure: the fix went to the call site the RCA was looking at, not to its siblings.***

## What changes

**`candy/plugin-check/bed_readiness.go`** — *a new `const initialReadyDeadline = 10 * time.Minute`, with the reasoning inline.* **Separate from the rebuild's 5 on purpose:** *a fresh create can meet a first-boot guest (`vmSshReadyProbe` deliberately excludes `WaitForCloudInit` from the reconnect condition, so `deploy-add` never races a still-running first-boot pacman) while a rebuild meets a reboot.* *10 min is 2× the rebuild's 5 and 1/3 of the 30-minute cap-only window this hop used to consume silently.*

**`candy/plugin-check/bed_run.go`** — *`waitReady` returns `error` and its VM/kubevirt arm runs under `waitVenueReady(ctx, initialReadyDeadline, …)`, so a lease-less guest becomes a **named, time-bounded failure**.* **And all five call sites now go through `phase("wait-ready", …)`, so the hop emits `[wait-ready] START` and its duration where it previously emitted nothing:**

| site | what it precedes |
|---|---|
| **the vm path** | *`step("deploy-add", …)` — **the reported site*** |
| *the kubevirt root path* | *the nested children* |
| *the `start` path* | *the nested children* |
| *the pod fresh-rebuild path* | *`step("feature-run-rebuild", …)`* |
| *`waitRebuildReady`'s container arm* | *returned rather than discarded* |

## A note that matters for review: the compiler did NOT catch this

**Go permits discarding a call's return value as a statement**, so making `waitReady` return an `error` produced **no build breakage at any of the five sites**. *A missed caller would have silently discarded the deadline failure and continued into the next step — worse than the stall, because a stall is at least visible as a non-completion.* **All five were fixed by hand for that reason**, and they are listed above so a reviewer can check them one by one.
