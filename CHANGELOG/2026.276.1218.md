# 2026.276.1218 — fix(check): allowlist the kubectl API-deprecation Warning: class (warnings=0 on the VM beds)

## Summary

Add one narrow `diagnosticAllowance` so the `severity-prefix` recognizer stops counting the **kubectl API-deprecation** warning the stock k3s addon manifests emit:

```
Warning: spec.template.spec.affinity.nodeAffinity.requiredDuringSchedulingIgnoredDuringExecution.nodeSelectorTerms[1].matchExpressions[0].key: node-role.kubernetes.io/master is use "node-role.kubernetes.io/control-plane" instead
```

k3s's Traefik / local-path-provisioner manifests still select the legacy `node-role.kubernetes.io/master` node label, so kubectl prints this on **every** bed whose deploy applies them. It is the single un-allowlisted `severityWarning` (`warnings=1`, `allowlisted=7`) on the `deploy-add` step of `check-kubevirt-operator` runs `2026.276.0239` / `.0810` / `.0904` and the `check-k3s-vm` runs — which is why R1's zero-warning bar is currently unreachable there.

The manifests are k3s's, not charly's: charly cannot remove the warning at its source without forking the k3s addon set, and the apply exits 0. A reviewed exemption is the correct instrument — the same mechanism the file's existing entries use.

Head `c303d49a8b03496c840d6408387bb999128f49a2` (branch `feat/allowlist-pacman-warnings`).

Fixes `opencharly/plugin-check#71`.
