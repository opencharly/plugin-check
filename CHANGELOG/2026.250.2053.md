# 2026.250.2053 — fix(check): serialize sessionHandle lifecycle transitions (session_service -race)

## Summary

The session_service -race run is RED: five session tests fail under -race on main:
`TestSpawnSessionSetsidLifecycle`, `TestOrphanSweepReapsStaleSession`,
`TestSweepToleratesHandlelessStateDir`, `TestFinalizeSessionDir`,
`TestSpawnSessionStopEscalates`. All five share ONE root cause: the
`sessionHandle` struct is shared mutable state between the reaper goroutine
(`spawnSetsidProcess`'s background `cmd.Wait()` + stop transition), the stop
path (`stopSession`) and the persisted write (`writeSessionHandle` marshal) —
the -race report pair is `session_service.go:243` (reaper writes `h.Status` /
`h.StoppedAt`) vs `:310` (`stopSession` reads the same fields) with
`writeSessionHandle`'s whole-struct marshal (`:298`) in between. A 30s
recorder dies the moment `stopSession` SIGTERMs it, so the reaper fires DURING
the stop — the race is not theoretical.

**Fix (RCA → root fix):** serialize every lifecycle-field access and every
persisted write on the handle's own `sync.Mutex`:

- `sessionHandle.mu` guards Status/StoppedAt/Transport/PID/Unit + the JSON
  write (`writeSessionHandle` now locks; `persistLocked` writes under the
  held lock — one consistent snapshot, never a torn marshal).
- `markStopped()` = locked transition + persist (idempotent; the reaper and
  `stopSession` may fire concurrently).
- `isStopped()` / `snapshot()` = locked reads (SessionLiveness and the
  lifecycle test no longer read raw fields off a handle a goroutine may be
  transitioning).
- Call sites: the reaper goroutine and `stopSession` now both go through
  `markStopped`; `SessionLiveness` reads through `snapshot()`.

No behavior change: same transitions, same persisted handle.json shape (mu is
unexported, excluded from the JSON).
